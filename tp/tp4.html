TP4 – Comptes et données avec Firebase

React Native · En trinôme · Projet, jalon 3

Votre application navigue et lit son API publique. Elle va maintenant reconnaître ses utilisateurs et garder leurs données sur un serveur : un compte par utilisateur, trois collections Firestore et des règles de sécurité qui protègent chacune d'elles.

Ce TP en bref

  • Chacun écrit au moins un des trois CRUD. Indiquez dans le README qui a fait quoi.
  • Ce jalon n'est pas noté à part. Ses critères font partie de la grille de production du projet, évaluée le 17 décembre.
  • Le cours 4 (favoris annotés des séjours) vous sert de modèle.

1 Brancher Firebase

SDK JavaScript · variables d'environnement
  1. Un membre crée le projet dans la console Firebase et y invite les deux autres (Paramètres du projet, onglet Utilisateurs et autorisations). Activez E-mail/Mot de passe dans Authentication. Créez la base Firestore en mode production, région eur3.
  2. Ajoutez une application Web au projet pour obtenir sa configuration.
  3. Installez le SDK avec npx expo install firebase @react-native-async-storage/async-storage.
  4. Créez .env.example (versionné, sans valeurs) et .env.local (non versionné, avec les valeurs de la console). Expliquez dans le README comment passer de l'un à l'autre.
  5. Copiez les trois fichiers ci-dessous tels quels.
EXPO_PUBLIC_FIREBASE_API_KEY=
EXPO_PUBLIC_FIREBASE_AUTH_DOMAIN=
EXPO_PUBLIC_FIREBASE_PROJECT_ID=
EXPO_PUBLIC_FIREBASE_STORAGE_BUCKET=
EXPO_PUBLIC_FIREBASE_MESSAGING_SENDER_ID=
EXPO_PUBLIC_FIREBASE_APP_ID=
// Les types publics de Firebase oublient cette fonction, pourtant
// bien présente sur mobile : on la déclare nous-mêmes
import { Persistence, ReactNativeAsyncStorage } from "firebase/auth";

declare module "firebase/auth" {
  export function getReactNativePersistence(
    storage: ReactNativeAsyncStorage,
  ): Persistence;
}
import AsyncStorage from "@react-native-async-storage/async-storage";
import { initializeApp } from "firebase/app";
import {
  getAuth,
  getReactNativePersistence,
  initializeAuth,
} from "firebase/auth";
import { getFirestore } from "firebase/firestore";
import { Platform } from "react-native";

// Configuration publique du projet : elle identifie le projet mais ne
// protège rien. Ce sont les règles de sécurité qui protègent les
// données
const firebaseConfig = {
  apiKey: process.env.EXPO_PUBLIC_FIREBASE_API_KEY,
  authDomain: process.env.EXPO_PUBLIC_FIREBASE_AUTH_DOMAIN,
  projectId: process.env.EXPO_PUBLIC_FIREBASE_PROJECT_ID,
  storageBucket: process.env.EXPO_PUBLIC_FIREBASE_STORAGE_BUCKET,
  messagingSenderId:
    process.env.EXPO_PUBLIC_FIREBASE_MESSAGING_SENDER_ID,
  appId: process.env.EXPO_PUBLIC_FIREBASE_APP_ID,
};

const app = initializeApp(firebaseConfig);

// Sur le web, la session est gardée par le navigateur. Sur mobile, il
// faut indiquer où la ranger : AsyncStorage
export const auth =
  Platform.OS === "web"
    ? getAuth(app)
    : initializeAuth(app, {
        persistence: getReactNativePersistence(AsyncStorage),
      });

export const db = getFirestore(app);
N'activez jamais le mode test de Firestore : il ouvre toutes vos données à tout le monde. La configuration de Firebase n'est pas secrète, mais elle ne protège rien. Seules les règles de l'étape 4 protègent vos données.

2 L'authentification

Firebase Auth · Context · Stack.Protected
  1. Écrivez le modèle de l'utilisateur dans src/models/user.ts et le service src/services/auth-service.ts : inscription, connexion, déconnexion, écoute de la session et traduction des erreurs en messages lisibles.
  2. Écrivez un Context d'authentification dans src/context/ et son hook useAuth dans src/hooks/. Il expose l'utilisateur connecté et indique si Firebase a fini de vérifier la session.
  3. Créez un groupe src/app/(auth)/ avec un écran de connexion (sign-in.tsx) et un écran d'inscription (sign-up.tsx), sans _layout.tsx dans ce groupe.
  4. Dans la pile racine, protégez vos écrans avec Stack.Protected : les onglets et le détail pour un utilisateur connecté, (auth)/sign-in et (auth)/sign-up pour un visiteur.
  5. Ajoutez un moyen de se déconnecter, par exemple un onglet « Compte ».
Indice : lire l'utilisateur dans la pile racine

Un composant ne peut pas lire le Context qu'il fournit lui-même. Placez les Providers dans RootLayout, puis écrivez la pile dans un petit composant placé sous eux, qui appelle useAuth().

Indice : « Page introuvable » après la déconnexion

Si le groupe (auth) a son propre _layout.tsx, Expo Router redirige vers /(auth), qui n'est pas une page. Retirez ce fichier et déclarez (auth)/sign-in et (auth)/sign-up directement dans la pile racine.

Indice : les codes d'erreur

Une erreur de Firebase est une FirebaseError avec un code, par exemple auth/invalid-credential ou auth/email-already-in-use. Un switch sur ce code donne le message à afficher.

3 Les trois CRUD

Firestore · services · temps réel

Choisissez trois collections utiles à votre sujet, par exemple des favoris annotés liés au catalogue, des recettes personnelles et une liste de courses. Chacun de vous en prend au moins une.

  1. Rangez les données de chaque utilisateur sous son identifiant : users/{uid}/recipes, par exemple. Chacun ne voit ainsi que ses propres données.
  2. Pour chaque collection, écrivez :
    • le modèle dans src/models/ ;
    • le service dans src/services/, qui crée, lit, modifie et supprime, et traduit chaque document en objet du modèle ;
    • le hook dans src/hooks/, que les écrans appellent. Aucun appel à Firebase dans src/app/ ni dans src/components/.
  3. Au moins une collection se lit en temps réel avec onSnapshot. Son hook s'abonne au montage et se désabonne au démontage.
  4. Chaque écran gère ses états : chargement, erreur, liste vide. Une écriture qui échoue affiche un message.
  5. Décrivez dans le README le schéma des trois collections : leur chemin et les champs de leurs documents.
Indice : tester le temps réel

Ouvrez l'application sur le web et sur Expo Go, connectés au même compte. Une modification d'un côté doit apparaître de l'autre sans rien recharger. Vous pouvez aussi modifier un document directement dans la console Firebase.

Indice : une seule collection pour tous les utilisateurs

Si vos documents doivent être vus par plusieurs utilisateurs (des avis publics, par exemple), gardez une collection commune et enregistrez l'auteur dans un champ ownerId. Les règles vérifient alors ce champ.

4 Les règles de sécurité

firestore.rules · Rules Playground
  1. Écrivez vos règles dans un fichier firestore.rules à la racine du dépôt, puis publiez-les dans la console (onglet Règles de Firestore).
  2. Chaque utilisateur ne peut lire et écrire que ses propres données. Tout le reste est refusé.
  3. À l'écriture, vérifiez la forme du document : les champs attendus, leur type, une longueur maximale pour les textes.
  4. Testez au moins trois cas dans le Rules Playground : un visiteur non connecté, le bon utilisateur, un autre utilisateur.
Indice : la structure d'une règle

Un bloc match /users/{userId}/recipes/{recipeId} désigne les documents d'une collection. Dans ce bloc, allow read: if request.auth != null && request.auth.uid == userId; réserve la lecture au propriétaire. Le document envoyé à l'écriture se lit dans request.resource.data.
