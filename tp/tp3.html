La notation

1 La navigation

Expo Router · Stack · Tabs
  1. Réorganisez src/app/ :
    • une pile racine dans src/app/_layout.tsx, qui garde votre Provider ;
    • un groupe (tabs) avec au moins deux onglets, chacun avec un titre et une icône ;
    • une route dynamique pour le détail d'un élément, par exemple src/app/recipes/[id].tsx ;
    • un écran +not-found.tsx avec un lien de retour à l'accueil.
  2. Déclarez unstable_settings = { anchor: "(tabs)" } dans la pile racine, pour qu'un détail ouvert par son URL garde une flèche de retour.
Importez Tabs depuis expo-router/js-tabs. Installez les icônes avec npx expo install @expo/vector-icons, jamais avec npm install : la commande d'Expo choisit la version compatible avec votre SDK.

2 L'API publique

fetch · async · typage
  1. Choisissez l'API de votre sujet et notez son adresse dans le README. Elle doit être gratuite et sans clé secrète.
  2. Ouvrez une réponse de l'API dans votre navigateur. Écrivez le type de la réponse, limité aux champs que vous utilisez.
  3. Remplacez le contenu de votre service par un appel à fetch :
    • vérifiez response.ok et levez une erreur sinon ;
    • convertissez la réponse en objets de votre modèle. Le reste de l'application ne doit pas connaître les noms de champs de l'API.
  4. Vérifiez que vos hooks et vos composants n'ont pas changé. Si vous avez dû les modifier, c'est qu'une responsabilité était mal placée au TP2.
  5. Coupez le réseau (mode avion ou outils de développement du navigateur) : l'erreur et le bouton « Réessayer » doivent s'afficher.
Indice : l'API renvoie beaucoup plus de champs que nécessaire

C'est normal. Ne typez que ce que vous utilisez, puis construisez vos objets du modèle avec les bons noms. Un champ facultatif de l'API devient une propriété facultative (?) de votre type.

Indice : les données locales servent encore

Si votre API ne fournit pas tout (vos catégories, par exemple), gardez ces données dans src/data/. Ce sont vos deux CRUD Firebase du TP4 qui remplaceront le reste.

3 L'écran de détail

useLocalSearchParams · liens profonds
  1. Depuis le catalogue, un appui sur un élément ouvre son détail avec router.push ou un <Link>.
  2. Le détail lit l'identifiant avec useLocalSearchParams et recharge l'élément par un service et un hook dédiés.
  3. Son titre apparaît dans l'en-tête (<Stack.Screen options>).
  4. Un identifiant inconnu affiche un message clair, sans planter.
Le test qui compte Sur le web, ouvrez un détail, puis rechargez la page (F5) et copiez son adresse dans un nouvel onglet. Le même détail doit s'afficher, avec une flèche de retour.

4 Le catalogue et ses filtres

FlatList · SectionList · hooks
  1. Le catalogue affiche les données de l'API en grille sur ordinateur et en liste sur téléphone.
  2. Il propose au moins deux filtres combinables (une recherche et une catégorie, par exemple). Leur logique est dans le modèle et dans un hook, jamais dans un composant.
  3. Un des écrans utilise une SectionList pour présenter des éléments groupés (par catégorie, par date…). La fonction de regroupement est dans le modèle.
  4. Chaque liste a une keyExtractor, un message quand elle est vide, et aucun calcul dans renderItem.

5 Le cycle de vie

useFocusEffect · AppState
  1. Repérez un écran dont les données peuvent changer pendant qu'il est caché (un onglet de favoris, par exemple). Rechargez-le avec useFocusEffect.
  2. Dans le README, expliquez en deux ou trois phrases pourquoi un useEffect(…, []) ne suffisait pas à cet endroit.
  3. Facultatif : rafraîchissez une donnée au retour de l'application au premier plan, avec AppState.
