01

Le module

Organisation du module

Une base de code, trois plateformes

iOS

De vrais composants natifs, affichés par le système du téléphone

Android

Le même code TypeScript, sans réécrire l'application en Kotlin

Web

React Native for Web transforme <View> en <div> dans le navigateur
  • Vous connaissez React. Vous allez réutiliser vos réflexes : composants, props, état, hooks
  • Ce qui change : pas de HTML ni de CSS, des contraintes mobiles (tactile, taille d'écran, réseau, cycle de vie)
Demander qui a déjà fait du React Native, du Flutter ou du natif.

Objectifs du module

À la fin du module, vous serez capables de :

  • Maîtriser React Native et son extension web pour concevoir une application performante à partir d'une base de code unique
  • Structurer votre application selon le pattern MVC : composants d'affichage, hooks et services pour la logique, modèles de données typés
  • Concevoir des interfaces réactives et fluides avec les composants natifs, le rendu web et Flexbox
  • Gérer le cycle de vie, la navigation et la persistance des données de manière unifiée entre le navigateur et le mobile

Programme

Cours 1 · Fondations

Architecture, React Native for Web, Expo, TypeScript, composants de base, Flexbox et responsive

Cours 2 · Architecture

Pattern MVC dans React, hooks personnalisés, services, modèles typés, état global avec Context

Cours 3 · Navigation

Expo Router (pile, onglets, URL, liens profonds), cycle de vie, listes volumineuses

Cours 4 · Persistance

Firebase : authentification, base Firestore, temps réel et règles de sécurité. Mise en production
Au plus 1h30 de théorie par demi-journée, le reste en pratique. Chaque notion est appliquée dans un TP le jour même.

Le projet

Organisation du module

Une application multiplateforme en trinôme

  • Sujet libre, à faire valider par moi aujourd'hui
  • Groupes de trois, formés aujourd'hui. Les groupes d'une seule personne ne sont pas possibles
  • Le projet avance à chaque TP. Chaque TP est un jalon du projet final
  • Chaque membre est propriétaire d'une partie (catalogue, navigation et compte, données partagées), avec son propre CRUD Firebase
  • Il doit fonctionner sur le web et sur mobile, avec le même code
TP2 · 28 oct.

TP3 · 29 oct.-24 nov.
Navigation, API publique, catalogue et filtres
TP4 · 25 nov.
Authentification et trois CRUD Firebase
17 déc.
Soutenance et rendu final

Ce que votre application doit contenir

Obligatoire

  • Au moins 4 écrans, avec des onglets, une pile et une route dynamique
  • L'URL du navigateur suit la navigation sur le web
  • Un catalogue responsive : grille sur ordinateur, liste sur mobile, avec des filtres
  • Une API publique consommée avec fetch()
  • Firebase : authentification et 3 CRUD, un par membre
  • Une architecture MVC en TypeScript
  • Une version web déployée (GitHub Pages…)
  • Un README exécutable qui suffit à lancer le projet

Valorisé

  • Une API native : caméra, localisation, notifications…
  • Des animations soignées
  • Un cache ou un mode hors ligne
  • Des tests automatisés

Des idées de sujets

Carnet de recettes

Catalogue de TheMealDB, favoris et recettes personnelles

Bibliothèque personnelle

Recherche dans Open Library, livres lus ou à lire et avis

Carnet de voyage

Pays de REST Countries, météo d'Open-Meteo, étapes et souvenirs

Garde-manger anti-gaspi

Produits d'Open Food Facts et dates de péremption. Le scan de codes-barres est un bonus
Toutes ces API sont gratuites et sans clé. Un autre sujet vous tente ? Proposez-le-moi : il doit se prêter à un catalogue et à trois CRUD.

Organisation du module

Modalités d'évaluation

ÉpreuveConditionsPoids

Aucune note intermédiaire. Tout est évalué le 17 décembre : avancez à votre rythme, mais régulièrement.
Règle ESGI : 50 % de contrôle continu et 50 % d'examen. MyGES donne le même poids à chaque note saisie : on saisit donc deux notes, la note de projet (moyenne de la production et de la soutenance) et l'écrit.

La note de projet : deux parties

Production · note du groupe

  • 20 critères à 1 point : rempli ou non
  • Un socle commun, puis 4 critères par partie
  • Corrigée sur le dernier commit poussé le 17 décembre avant 23h59

Soutenance · note individuelle

  • Démonstration de votre partie
  • Explication d'un extrait de votre code, que je choisis
  • Une question sur la partie d'un autre membre
Votre note de projet est la moyenne de ces deux notes. La grille complète est dans le sujet du projet. Un membre qui n'a pas contribué peut voir sa note de production réduite, jusqu'à 0.
Le 25 novembre, point d'étape non noté de 5 min par groupe pendant le TP4 : repérer les groupes en retard et les membres absents du projet.

Le 17 décembre

Soutenance · 10 min par groupe

  • 4 min : démonstration sur le web et sur mobile, chacun présente sa partie
  • 2 min par membre : un extrait de votre code à expliquer, puis une question sur une autre partie
  • Rendu : dernier commit poussé le soir même avant 23h59

Examen écrit · 30 min

  • À la fin de la séance, après les soutenances
  • 10 questions à réponse courte (une à trois lignes) sur l'ensemble des cours, 2 points chacune
  • Plusieurs questions portent sur des extraits de code : prévoir ce qui s'affiche, trouver une erreur

L'IA générative : autorisée, à une condition

  • ChatGPT, Claude, Copilot… sont autorisés pour les TP et le projet
  • Vous devez comprendre votre code de bout en bout. Chaque membre du groupe doit pouvoir expliquer chaque partie
  • Déclarez votre usage dans le README : quels outils, pour quoi faire
  • Les questions de la soutenance vérifient cette compréhension. Une fonctionnalité non expliquée n'est pas comptée
  • L'examen écrit se fait sans IA
  • Le plagiat et la triche entraînent un 0 à l'épreuve concernée
Conseil : utilisez l'IA comme un tuteur (expliquer une erreur, relire votre code), pas comme un auteur.
