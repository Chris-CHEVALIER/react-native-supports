Pourquoi une architecture ?

Le problème de l'écran « tout-en-un »

Un écran qui fait tout

// AVANT le refactoring : tout est dans l'écran (exemple à ne pas
// suivre)
import { useEffect, useState } from "react";
import {
  ActivityIndicator,
  FlatList,
  Pressable,
  Text,
  TextInput,
  View,
} from "react-native";

import { STAYS } from "@/data/stays";
import { Stay } from "@/models/stay";

export default function CatalogScreenBefore() {
  const [stays, setStays] = useState<Stay[]>([]);
  const [loading, setLoading] = useState(true);
  const [query, setQuery] = useState("");
  const [favorites, setFavorites] = useState<string[]>([]);

  useEffect(() => {
    setTimeout(() => {
      setStays(STAYS);
      setLoading(false);
    }, 600);
  }, []);

  if (loading) return <ActivityIndicator />;

  return (
    <View style={{ flex: 1, padding: 8 }}>
      <TextInput
        value={query}
        onChangeText={setQuery}
        placeholder="Rechercher"
      />
      <FlatList
        data={stays.filter((s) => s.title.includes(query))}
        keyExtractor={(s) => s.id}
        renderItem={({ item }) => (
          <Pressable
            onPress={() =>
              setFavorites(
                favorites.includes(item.id)
                  ? favorites.filter((f) => f !== item.id)
                  : [...favorites, item.id],
              )
            }
          >
            <Text>
              {favorites.includes(item.id) ? "★" : "☆"} {item.title} ·{" "}
              {item.pricePerNight} €
            </Text>
          </Pressable>
        )}
      />
    </View>
  );
}
  • Le chargement, les règles de recherche, les favoris et l'affichage sont mélangés
  • Rien n'est réutilisable dans un autre écran
  • Rien n'est testable sans afficher l'écran
  • Remplacer les données locales par une API oblige à réécrire l'écran
Faire lister les défauts par la classe avant d'afficher la colonne de droite. C'est le type de code qu'on retrouve souvent dans les premiers projets des étudiants.

02

Le pattern MVC dans React

Modèle, vue, contrôleur

MVC : trois rôles

RôleCe qu'il faitDans notre projet
ModèleDécrit les données et les règles métier, sans rien affichersrc/models/ : types et fonctions pures
src/services/ : accès aux données
ContrôleurTient l'état, réagit aux actions de l'utilisateur, appelle les servicessrc/hooks/ : hooks personnalisés
src/context/ : état partagé
VueAffiche ce qu'on lui donne et signale les actionssrc/components/ : composants purs
src/app/ : écrans qui assemblent
MVC vient des interfaces graphiques des années 1970. Dans React, le contrôleur n'est pas une classe : c'est un hook personnalisé.
Erreur fréquente : écrire la logique métier dans le hook. Les règles vivent dans le modèle, l'accès aux données dans les services. Le contrôleur ne fait qu'orchestrer : il les appelle et tient l'état.

Le trajet d'une action

1. Vue
L'utilisateur tape « Lyon ». StayFiltersBar appelle onChange({ query: "Lyon" })
2. Contrôleur
useStayFilters met à jour son état filters
3. Modèle
matchesFilters() décide quels séjours correspondent
4. Vue
React affiche à nouveau la liste avec les séjours visibles
Les données descendent par les props, les événements remontent par les fonctions de rappel. La vue ne modifie jamais les données elle-même.

Le modèle : types et règles

Des données décrites et des fonctions pures

Modéliser les données

export type StayType = "apartment" | "house" | "cabin";

export type Stay = {
  id: string;
  title: string;
  city: string;
  type: StayType;
  pricePerNight: number;
  available: boolean;
  latitude: number;
  longitude: number;
  imageUrl?: string;
};

export type StayFilters = {
  query: string;
  type: StayType | null;
  onlyAvailable: boolean;
};

export const STAY_TYPE_LABELS: Record<StayType, string> = {
  apartment: "Appartement",
  house: "Maison",
  cabin: "Cabane",
};

// Règle métier : une fonction pure, sans React, facile à tester
export function matchesFilters(
  stay: Stay,
  filters: StayFilters,
): boolean {
  const search = filters.query.trim().toLowerCase();
  const matchesQuery =
    stay.title.toLowerCase().includes(search) ||
    stay.city.toLowerCase().includes(search);
  const matchesType =
    filters.type === null || stay.type === filters.type;
  const matchesAvailability =
    !filters.onlyAvailable || stay.available;
  return matchesQuery && matchesType && matchesAvailability;
}
  • Les types sont le contrat entre toutes les couches
  • StayType | null : « aucun type choisi » est une valeur prévue
  • Record<StayType, string> : un objet avec une entrée par type. En ajouter un sans libellé est une erreur

Le contrôleur : services et hooks

Charger, filtrer, réagir

Le service : appeler l'API et convertir

import { Stay, StayType } from "@/models/stay";

const SITE = "https://chris-chevalier.github.io/react-native-supports";
const STAYS_URL = `${SITE}/api/stays.json`;

// Forme de la réponse de l'API, limitée à ce qu'on utilise
type StayResponse = {
  id: string;
  title: string;
  type: StayType;
  price_per_night: number;
  is_available: boolean;
  image_url: string | null;
  location: { city: string; latitude: number; longitude: number };
};

// Traduit une réponse de l'API dans le vocabulaire du modèle
function toStay(response: StayResponse): Stay {
  return {
    id: response.id,
    title: response.title,
    city: response.location.city,
    type: response.type,
    pricePerNight: response.price_per_night,
    available: response.is_available,
    latitude: response.location.latitude,
    longitude: response.location.longitude,
    imageUrl: response.image_url ?? undefined,
  };
}

export async function fetchStays(): Promise<Stay[]> {
  const response = await fetch(STAYS_URL);
  if (!response.ok) throw new Error(`Erreur HTTP ${response.status}`);
  const data: StayResponse[] = await response.json();
  return data.map(toStay);
}
  • StayResponse décrit la réponse de l'API avec ses noms : price_per_night, location.city…
  • toStay la traduit dans le vocabulaire du modèle. Le reste de l'application ne connaît jamais les noms de l'API
  • fetch fait un vrai appel réseau. Il ne lève pas d'erreur sur une réponse 404 ou 500 : testez response.ok
  • Le service tient sa promesse : Promise<Stay[]>. Si l'API change, seul ce fichier change
Ouvrir l'adresse du JSON dans le navigateur avant de montrer le code : comparer les noms de l'API et ceux du modèle. Faire échouer l'appel (modifier l'URL) pour montrer l'état d'erreur.

Un état qui ne peut pas mentir

import { useEffect, useState } from "react";

import { Stay } from "@/models/stay";
import { fetchStays } from "@/services/stays-service";

export type StaysState =
  | { status: "loading" }
  | { status: "error"; message: string }
  | { status: "success"; stays: Stay[] };

// Contrôleur : charge les séjours et expose un état que la vue sait
// afficher
export function useStays() {
  const [state, setState] = useState<StaysState>({
    status: "loading",
  });
  const [attempt, setAttempt] = useState(0);

  useEffect(() => {
    let cancelled = false;
    fetchStays()
      .then((stays) => {
        if (!cancelled) setState({ status: "success", stays });
      })
      .catch(() => {
        if (!cancelled)
          setState({
            status: "error",
            message: "Échec du chargement",
          });
      });
    return () => {
      cancelled = true;
    };
  }, [attempt]);

  const reload = () => {
    setState({ status: "loading" });
    setAttempt((n) => n + 1);
  };

  return { state, reload };
}
  • Une union discriminée : la propriété status indique la forme de l'objet
  • Impossible d'avoir à la fois une erreur et des données. Avec trois booléens (loading, error, data), huit combinaisons existent, dont cinq absurdes
  • Dans l'écran, après if (state.status === "error") return …, TypeScript sait que state ne peut plus être qu'en chargement ou en succès

Le hook useStayFilters : un état dérivé

import { useState } from "react";

import { matchesFilters, Stay, StayFilters } from "@/models/stay";

const INITIAL_FILTERS: StayFilters = {
  query: "",
  type: null,
  onlyAvailable: false,
};

// Contrôleur : l'état des filtres et la liste qui en découle
export function useStayFilters(stays: Stay[]) {
  const [filters, setFilters] =
    useState<StayFilters>(INITIAL_FILTERS);

  const updateFilters = (changes: Partial<StayFilters>) =>
    setFilters((current) => ({ ...current, ...changes }));

  const visibleStays = stays.filter((stay) =>
    matchesFilters(stay, filters),
  );

  return { filters, updateFilters, visibleStays };
}
  • visibleStays n'est pas un état : il se calcule à chaque rendu
  • Stocker une donnée calculable crée deux sources de vérité qui finissent par diverger
  • Partial<StayFilters> : toutes les propriétés deviennent facultatives
  • Le React Compiler, activé par Expo, évite les calculs inutiles : pas besoin de useMemo

Quiz

Je dois trier les séjours par prix. Où écrire la fonction de tri ?

Dans le modèle (src/models/stay.ts) : c'est une règle métier, pure et testable. Le hook l'appelle, la vue n'en sait rien.

Faut-il un useState pour le nombre de séjours visibles ?

Non : visibleStays.length se calcule. Un état ne doit contenir que ce qui ne se déduit de rien d'autre.

L'écran assemblé

import { useState } from "react";
import { FlatList, StyleSheet, Text, View } from "react-native";

import { StateMessage } from "@/components/state-message";
import { StayCard } from "@/components/stay-card";
import { StayFiltersBar } from "@/components/stay-filters-bar";
import { useColumns } from "@/hooks/use-columns";
import { useStayFilters } from "@/hooks/use-stay-filters";
import { useStays } from "@/hooks/use-stays";

// Écran : il assemble les contrôleurs (hooks) et les vues
// (composants)
export default function CatalogScreen() {
  const columns = useColumns();
  const { state, reload } = useStays();
  const stays = state.status === "success" ? state.stays : [];
  const { filters, updateFilters, visibleStays } =
    useStayFilters(stays);
  const [favorites, setFavorites] = useState<string[]>([]);
  const isFavorite = (id: string) => favorites.includes(id);
  const toggleFavorite = (id: string) =>
    setFavorites((current) =>
      current.includes(id)
        ? current.filter((f) => f !== id)
        : [...current, id],
    );

  if (state.status === "loading") return <StateMessage loading />;
  if (state.status === "error")
    return <StateMessage message={state.message} onRetry={reload} />;

  return (
    <View style={styles.container}>
      <View style={styles.header}>
        <Text style={styles.heading}>Séjours</Text>
        <Text style={styles.count}>{favorites.length} favori(s)</Text>
      </View>
      <StayFiltersBar filters={filters} onChange={updateFilters} />
      <FlatList
        key={columns}
        numColumns={columns}
        data={visibleStays}
        keyExtractor={(stay) => stay.id}
        renderItem={({ item }) => (
          <StayCard
            stay={item}
            isFavorite={isFavorite(item.id)}
            onToggleFavorite={toggleFavorite}
          />
        )}
        ListEmptyComponent={
          <Text style={styles.empty}>
            Aucun logement ne correspond.
          </Text>
        }
      />
    </View>
  );
}

const styles = StyleSheet.create({
  container: {
    flex: 1,
    width: "100%",
    maxWidth: 1100,
    alignSelf: "center",
    padding: 8,
  },
  header: {
    flexDirection: "row",
    justifyContent: "space-between",
    alignItems: "center",
    margin: 8,
  },
  heading: { fontSize: 24, fontWeight: "800" },
  count: { fontSize: 16, fontWeight: "600", color: "#0B7A70" },
  empty: { margin: 8, fontSize: 16 },
});
  • L'écran ne contient aucune règle : il branche les hooks sur les composants
  • Il gère les trois états : chargement, erreur, succès
  • Pour l'instant, les favoris sont un état local de l'écran
  • Les hooks sont appelés avant tout return : c'est une règle de React
Rappeler les règles des hooks : toujours au premier niveau du composant, jamais dans une condition ni après un return.

Check-list d'une vue pure

Une vue pure…

  • reçoit ses données par des props typées
  • signale les actions par des fonctions de rappel (onChange, onPress…)
  • peut avoir un petit état d'interface (un menu ouvert, un champ en cours de saisie)

Une vue pure ne…

  • n'importe aucun service et n'appelle ni fetch ni Firebase
  • ne contient aucune règle métier (calcul de prix, filtre, tri)
  • ne charge pas de données dans un useEffect
C'est la grille que j'utiliserai pour évaluer l'architecture du projet : séparation stricte des responsabilités.

L'état local et l'état global

Partager une donnée entre plusieurs écrans

Local ou global ?

État localÉtat global
ExempleLe texte d'une recherche, un menu ouvertLes favoris, l'utilisateur connecté, le panier
Utilisé parUn écran et ses enfants directsPlusieurs écrans éloignés
OutiluseState dans un composant ou un hookContext, ou une bibliothèque
Faire descendre une prop à travers cinq composants qui ne s'en servent pas s'appelle le prop drilling. C'est le signe qu'un état global est nécessaire.

Créer un Context typé

import { createContext, ReactNode, useState } from "react";

export type FavoritesContextValue = {
  favorites: string[];
  isFavorite: (id: string) => boolean;
  toggleFavorite: (id: string) => void;
};

export const FavoritesContext =
  createContext<FavoritesContextValue | null>(null);

export function FavoritesProvider({
  children,
}: {
  children: ReactNode;
}) {
  const [favorites, setFavorites] = useState<string[]>([]);

  const isFavorite = (id: string) => favorites.includes(id);
  const toggleFavorite = (id: string) =>
    setFavorites((current) =>
      current.includes(id)
        ? current.filter((f) => f !== id)
        : [...current, id],
    );

  return (
    <FavoritesContext.Provider
      value={{ favorites, isFavorite, toggleFavorite }}
    >
      {children}
    </FavoritesContext.Provider>
  );
}
  • Le type décrit ce que le Context met à disposition
  • null par défaut : la valeur n'existe que sous un Provider
  • Le Provider tient l'état et le transmet à tous ses descendants

Lire le Context avec un hook

import { useContext } from "react";

import {
  FavoritesContext,
  FavoritesContextValue,
} from "@/context/favorites-context";

// Seule porte d'entrée vers les favoris partagés
export function useFavorites(): FavoritesContextValue {
  const context = useContext(FavoritesContext);
  if (!context) {
    throw new Error(
      "useFavorites doit être utilisé dans un FavoritesProvider",
    );
  }
  return context;
}
  • Comme tout hook, il est rangé dans src/hooks/. Le fichier du Context ne contient que le Context et son Provider
  • Le hook useFavorites() est la seule porte d'entrée. Les écrans n'importent jamais le Context directement
  • L'erreur explicite signale un oubli du Provider dès le premier test
  • Après le if, TypeScript sait que context n'est plus null

export default function RootLayout() {
  return (
    <FavoritesProvider>
      <Stack screenOptions={{ headerTransparent: false }}>
        <Stack.Screen name="index" options={{ title: "Catalogue" }} />
      </Stack>
    </FavoritesProvider>
  );
}
  • _layout.tsx enveloppe tous les écrans : c'est l'endroit du Provider
  • Le Stack et ses options ne changent pas : le Provider l'entoure
  • Chaque modification de la valeur affiche à nouveau tous les composants qui lisent ce Context. Ne mettez pas tout dedans

Un composant qui lit le Context

import { StyleSheet, Text } from "react-native";

import { useFavorites } from "@/hooks/use-favorites";

// Lit les favoris dans le Context : aucune prop à recevoir
export function FavoritesBadge() {
  const { favorites } = useFavorites();
  return (
    <Text style={styles.badge}>★ {favorites.length} favori(s)</Text>
  );
}

const styles = StyleSheet.create({
  badge: { fontSize: 16, fontWeight: "600", color: "#0B7A70" },
});
  • Le badge importe le hook useFavorites, pas le Context
  • Aucune prop : il lit les favoris directement, où qu'il soit placé sous le Provider
  • Sans Context, il faudrait passer les favoris de parent en enfant jusqu'à lui

Le catalogue partage ses favoris

import { FlatList, StyleSheet, Text, View } from "react-native";

import { FavoritesBadge } from "@/components/favorites-badge";
import { StateMessage } from "@/components/state-message";
import { StayCard } from "@/components/stay-card";
import { StayFiltersBar } from "@/components/stay-filters-bar";
import { useFavorites } from "@/hooks/use-favorites";
import { useColumns } from "@/hooks/use-columns";
import { useStayFilters } from "@/hooks/use-stay-filters";
import { useStays } from "@/hooks/use-stays";

// Écran : il assemble les contrôleurs (hooks) et les vues
// (composants)
export default function CatalogScreen() {
  const columns = useColumns();
  const { state, reload } = useStays();
  const stays = state.status === "success" ? state.stays : [];
  const { filters, updateFilters, visibleStays } =
    useStayFilters(stays);
  const { isFavorite, toggleFavorite } = useFavorites();

  if (state.status === "loading") return <StateMessage loading />;
  if (state.status === "error")
    return <StateMessage message={state.message} onRetry={reload} />;

  return (
    <View style={styles.container}>
      <View style={styles.header}>
        <Text style={styles.heading}>Séjours</Text>
        <FavoritesBadge />
      </View>
      <StayFiltersBar filters={filters} onChange={updateFilters} />
      <FlatList
        key={columns}
        numColumns={columns}
        data={visibleStays}
        keyExtractor={(stay) => stay.id}
        renderItem={({ item }) => (
          <StayCard
            stay={item}
            isFavorite={isFavorite(item.id)}
            onToggleFavorite={toggleFavorite}
          />
        )}
        ListEmptyComponent={
          <Text style={styles.empty}>
            Aucun logement ne correspond.
          </Text>
        }
      />
    </View>
  );
}

const styles = StyleSheet.create({
  container: {
    flex: 1,
    width: "100%",
    maxWidth: 1100,
    alignSelf: "center",
    padding: 8,
  },
  header: {
    flexDirection: "row",
    justifyContent: "space-between",
    alignItems: "center",
    margin: 8,
  },
  heading: { fontSize: 24, fontWeight: "800" },
  empty: { margin: 8, fontSize: 16 },
});
  • Le catalogue importe le badge et le hook des favoris
  • Les favoris ne sont plus un état local de l'écran : ils viennent du Context
  • <FavoritesBadge /> se met à jour à chaque favori ajouté, sans recevoir de props

Quiz

Un composant appelle useFavorites() mais l'application plante avec « useFavorites doit être utilisé dans un FavoritesProvider ». Pourquoi ?

Le composant n'est pas à l'intérieur du FavoritesProvider. Il faut l'ajouter au-dessus, en général dans _layout.tsx.

Le texte d'un champ de recherche doit-il aller dans un Context ?

Non. Il ne sert qu'à un écran : un état local suffit. Le Context est réservé à ce que plusieurs écrans partagent.

À retenir

  • Modèle : des types et des fonctions pures dans models/, l'accès aux données dans services/
  • Le service appelle l'API et convertit sa réponse en objets du modèle
  • Contrôleur : des hooks personnalisés qui tiennent l'état et appellent les services
  • Vue : des composants qui reçoivent des props et signalent des événements
  • Un état en union discriminée rend les états absurdes impossibles
  • Ce qui se calcule ne se stocke pas
  • Context pour l'état partagé entre composants, exposé par un hook rangé dans src/hooks/
